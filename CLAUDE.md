<!-- K-433: /printing-press-import go.mod rewrite silently fails on CRLF line endings -->
- When writing `perl -pi -e` substitutions over text whose line endings you don't own (downloaded library tarballs, cross-platform staging, generator output), treat `\$` end-anchors as unsafe — on CRLF lines `$` lands between `\r` and `\n`, so a pattern like `s|^module \Q...\E\$|...|` silently misses. Bound with `\s+` (`s|^module\s+\Q...\E|...|`) or strip `\r` first (`perl -pi -e "s/\r\$//"`). After every `go.mod` module-path rewrite, assert with `grep -Eq "^module[[:space:]]+<expected>"` and exit non-zero on failure.
<!-- K-434: printing-press publish validate blocks on missing tools-manifest.json for pre-4.x CLIs -->
- `publish validate`'s `manifest` check requires `tools-manifest.json` at the CLI root for any MCP-advertising CLI. Older press versions (≤3.x) didn't emit it; their CLIs fail validate, and `publish package` runs validate first and refuses too. **Fix:** run `printing-press tools-manifest emit --dir <cli-dir>` — this is the cross-platform recovery path (works on Windows where `regen-merge` does not). The command re-parses the archived spec via the same `pipeline.WriteToolsManifest` the generator uses, so the emitted file matches what a current-press regen would produce. Inspect `.printing-press.json` for `printing_press_version` before suggesting publish; if older or `tools-manifest.json` is missing, run `tools-manifest emit` first.
<!-- K-765: HTTP Basic auth is api_key + a two-placeholder format, and both adjacent defaults break the CLI -->
- There is no `auth.type: basic` — declare HTTP Basic auth as `type: api_key` with `header: "Authorization"` and `format: "Basic {api_id}:{api_token}"`; the generator derives the env vars from the placeholders, base64-encodes `id:token`, and requires **both** before `AuthHeader()` returns anything (OpenAPI equivalent: `type: http` / `scheme: basic` + `x-auth-format`, mapped by the `case "basic"` branch in `internal/openapi/parser.go`). Always set `auth.verify_path` explicitly on any API with a partner/app tier alongside customer keys (Aircall, Stripe, Slack, HubSpot) — `deriveAuthVerifyPath` picks a "me-shaped" GET (`/me`, `/users/me`, `/account`, `/viewer`, `/self`) for the doctor probe, which on Aircall selected the OAuth-partner-only `/v1/integrations/me` and made `doctor` report `WARN Credentials: scope-limited (HTTP 403)` forever against valid credentials. With two credentials, expect six failing tests in the generated `internal/cliutil/credentials_test.go` — it is emitted from the singular `.Auth.CanonicalEnvVar`, so the fixtures populate only the first and `AuthHeader()` can never resolve; that is a generator gap, not a spec error, so do not chase it. Verify the wiring with `doctor`: anything under `OK Env Vars: OK 2/2 available` means a placeholder name and an env var name disagree.
<!-- K-778: OAuth2 refresh should send client credentials as HTTP Basic, not body params -->
- In any OAuth2 token exchange, a **confidential** client (one with a secret) authenticates with `req.SetBasicAuth(clientID, clientSecret)` and puts **nothing** credential-shaped in the body — RFC 6749 §2.3.1 makes `client_secret_basic` the mechanism every server MUST support while body params are only MAY, and §2.3 forbids presenting both at once; a **public** client (no secret) sends `client_id` in the body per §3.2.1. The reason is credential hygiene plus conformance, **not** provider rejection: body params put the OAuth *application* secret in the place proxies and access logs capture most readily, for the less universally supported mechanism. Do **not** repeat the retracted claim that Intuit rejects body-only refresh with `invalid_client` — it accepts both; that finding came from a probe whose arms both used a bogus `client_id`, so `invalid_client` was reporting an unrecognized client, not a rejected mechanism. The real tell is two token-exchange paths in one client authenticating differently — `refreshAccessToken` must match the `client_credentials` mint. Both `client.go.tmpl` paths are fixed and use `SetBasicAuth` (the mint and `refreshAccessToken`); keep them that way, and grep for `SetBasicAuth` rather than trusting a line number — the retracted-Intuit sentence that used to sit above the refresh call was removed in #38, so the old `:2347` pointer no longer resolves. **Two sites still send `client_secret` in the body and are not yet fixed:** the authorization-code exchange in `auth.go.tmpl` and `RefreshToken` in `oauth_device.go.tmpl`. They are deferred deliberately — moving them is a wire-format change against live providers with its own compat surface (INC-2026-776), not a drive-by. (INC-2026-540)
<!-- K-778b: a negative probe needs a positive control -->
- Before treating a failed probe as evidence, ask what it would have shown **if the hypothesis were false**. If the answer is "the same thing," it is not evidence. Two arms that fail identically prove they are equivalent only when a known-good arm *succeeds* — run that positive control, and watch for the error *code* changing (`invalid_client` → `invalid_grant`) rather than for failure-vs-failure. Keep a correct fix while retracting an unverified impact claim; a right patch must not launder a wrong story into the permanent record.
<!-- K-779: quote every value emitted into a shell from scratch; never detect "already quoted" -->
- When emitting a command line anyone will paste (generated docs, README examples, CI snippets, error-message suggestions), **quote every interpolated value from scratch** and pass through only an exact, enumerated allowlist of the literals this codebase itself emits pre-quoted (`preQuotedExampleValues` in `internal/generator/first_command_example.go`). Never decide "it already looks quoted" from the first and last character — that check accepts `'safe'; rm -rf /; echo 'safe'`, handing whoever controls a spec field or API response control of what runs. Use single quotes only (POSIX suspends every expansion inside them, so one rule covers globs, `$var`, command substitution, backticks, word splitting and `!` history expansion) with the close-escape-reopen idiom for an embedded quote, and keep `!` in the sensitive set — it misbehaves only in a real terminal, never in CI. Test the round trip: assert the quoted value tokenizes back to one argument through the consumers' own tokenizer, never string-equality on the quoted form. (INC-2026-554)
<!-- K-785: `auth status` reports token PRESENCE; only `doctor` reports validity -->
- Never gate on `{tool}-pp-cli auth status` - it reads the local `config.toml` and reports token PRESENCE, so a rejected refresh token still prints `Authenticated` and exits 0; only `{tool}-pp-cli doctor` makes the live call that surfaces `FAIL API: unreachable: refresh token rejected (invalid_grant)`. Credentials live in `C:\Users\{user}\.config\{tool}-pp-cli\config.toml`, never a project `.env`, so exit code 4 (auth required) is not a project misconfiguration and is repaired only by `{tool}-pp-cli auth login` - a browser flow, therefore a human action; never paste a token. See K-785.
<!-- K-786: `--help` text can be wrong - `--dry-run` every documented CLI example -->
- Before committing any CLI example into a doc, skill, or instruction file, run it with `--dry-run` (needs no valid auth) - `--help` and a shipped `SKILL.md` are claims, not facts, and were both wrong on `google-search-console-pp-cli` 1.0.0: `--dimensions` requires a JSON array `'["QUERY"]'` on `query-search-analytics` but a plain comma list on `sync`, and the site argument is positional on every command except `sync`, where it is `--site`. Never gate a dry-run on its exit code - a validation failure prints the error to stdout and still exits 0. See K-786.
<!-- K-787: Windows `auth login` truncates the OAuth URL at `&` - use `--no-browser` -->
- On Windows, always run `{tool}-pp-cli auth login --no-browser` - the plain `auth login` hands the authorization URL to `cmd /c start` unquoted, `cmd.exe` cuts it at the first `&`, and the browser receives 1 of 9 OAuth params, so Google returns `Error 400: invalid_request - Required parameter is missing: response_type`. That error describes the truncated request, NOT the OAuth client - do not go diagnose it in the Google Cloud Console. `--no-browser` prints the full URL and waits on its `127.0.0.1:<port>/callback` listener; the PKCE challenge and the port are per-invocation, so keep the command running and never reuse a URL from an earlier run. A failed `auth login` zeroes the stored tokens while leaving `client_id`/`client_secret` intact, so "no refresh token" afterwards is not evidence that setup was lost. See K-787.
<!-- K-790: pp-cli response cache was keyed on the request, NOT the credential (FIXED) -->
- **Fixed in the templates and in every shipped CLI; the `--no-cache` workaround is no longer required.** The response cache at `~/.cache/{tool}-pp-cli/responses/<hash>.json` was keyed on method+path+params and NOT on the credential, so a second account was silently served the first account's data with no error and a completely plausible shape. `cacheKey` now mixes in `base_url`, `auth_source`, a sha256 of the resolved auth header, and the config path (`client.go.tmpl`), and the cache is written `0700`/`0600` rather than `0755`/`0644` (`cache.go.tmpl`). SearchActions/cli#59 swept the same two defects across 22 already-shipped CLIs and added mutation-proven `conformance.sh` assertions for both. Still applies to any CLI printed by a press older than ~4.28.0 that has not been swept. On one of those, two accounts returning byte-identical results *may* be a cache hit — but per K-778b above, that observation is only evidence once a control could have distinguished the two: purge first (`rm -- "$HOME/.cache/<tool>-pp-cli/responses/"*.json` — quote the path, leave only the `*.json` glob outside the quotes, per K-779), then re-run both. Identical again after a cold cache means the accounts genuinely see the same data, which is common on shared or empty tenants; differing means it was the cache. (INC-2026-775, K-790.)
